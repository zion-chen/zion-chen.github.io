登录校验详解：Cookie、Session、Token 和 JWT

发表于2025-10-22|Java学习

一、登录校验的核心流程

无论使用哪种方式进行登录校验，本质上的流程是一样的：

  1. 第一次访问网站：浏览器传来用户信息，服务端查库校验，在服务端保存登录状态，并给浏览器返回一个登录凭证。
  2. 后续多次访问网站：浏览器在每次请求中都携带登录凭证，向服务端证明用户处于已登录状态，服务端的过滤器/拦截器校验通过后直接放行，进行后续业务逻辑。

二、登录校验的基石：Cookie 和 Session 简介

（一）Cookie - 浏览器端

  • Cookie 是服务器保存在客户端浏览器中的一小段文本信息，存储位置在客户端（浏览器）。
  • 对一个浏览器来说，如果某网站设置了一个 Cookie，那么下次再请求该网站时，在请求头中会自动加上该网站设置的 Cookie。

（二）Session - 服务器端

Session 是服务器为每个用户单独创建的会话数据，Tomcat 默认把 Session 存在服务器内存中。Session 通常以键值对的形式存储：

三、Session 校验：最简单的登录校验

借助 Cookie，我们可以在前后端之间传输信息；而借助 Session，我们则可以为当前用户单独开辟一块空间，存储只属于当前用户的信息。这样一来，我们就可以用 Session 存储用户的登录状态，从而实现简单的登录校验。

（一）校验流程

得益于 Tomcat，我们在服务端创建 Session 时，Tomcat 会自动在响应中给 Cookie 设置对应的 SessionID。

1️⃣ 第一次访问网站，需要登录

  • 浏览器访问网站，这时浏览器发送的请求中并没有携带登录相关的 Cookie。
  • 服务器检测到 Cookie 中没有 SessionID，于是：
    • 创建一个新的 Session ，自动在响应中给 Cookie 传去 SessionID
    • 根据用户传来的用户名和密码去查库
    • 在 Session 中保存查到的用户对象，作为登录状态

响应头大概如下：

``vbnet
HTTP/1.1 200 OK
Set-Cookie: JSESSIONID=abc123

服务器拿到 SessionID：abc123，就能从内存中找到该用户的 Session，能找到 Session 就认定用户已登录，也就完成了登录校验。

代码示例：

  • 其余请求：获取 Session，在拦截器中做登录校验

注意到，第一次登录和后续校验都用到了HttpSession session = request.getSession();这行代码，但第一次是新建 Session，第二次是获取对应的 Session。Tomcat是这样处理这行代码的：

  1. 在服务器内存中查找 Session Map，看是否存在 JSESSIONID=abc123 对应的 Session
  2. 如果找到 → 返回该 Session 对象
  3. 如果找不到（比如过期或被销毁了/前端根本没传来 SessionID）：
    • getSession() → 会自动创建一个新的 Session
    • getSession(false) → 返回 null（不创建新的）

（二）Cookie、Session和浏览器的关系

我使用浏览器A访问网站，存储了 Cookie；又使用浏览器B访问网站，登录同一个账号，存储的 Cookie 和浏览器A是一样的吗?

答案是不一样。

  1. 首先，两个浏览器互相看不到对方存储的 Cookie。
  2. 服务端创建 Session 的时候并不知道要存什么内容，所以就算存相同的用户数据，SessionID 也不可能相同。就算在同一个浏览器里，第二次登录创建的 SessionID 肯定也和之前的不一样。

（三）Session 的存储方式

显然，服务端只是给 Cookie 一个 SessionId，而 Session 的具体内容（可能包含用户信息、Session 状态等），都要储存在服务端。存储的方式有几种：

  • Redis（推荐）：以 key-value 的形式存，正合 SessionId - Session 的场景，且访问快。
  • 服务器内存：直接放到变量里，一旦服务重启就没了。
  • 数据库：普通数据库，性能不高。

三、Token：解决 Session 的痛点

（一）Session 的问题

Session 的维护给服务端造成很大困扰：我们必须找合适的地方存放它，又要考虑分布式的问题，甚至要单独为了它启用一套 Redis 集群。有没有更好的办法？

我们来重新审视一下之前写的 Session 校验的流程：

我们只要根据 SessionID 查到了对应的 Session，就认定用户已登录，而 Session 中所储存的用户信息，我们最多也只需要一个用户ID用于后续的业务处理。这样看来，这么少的数据量，根本没必要在服务端的 Session 中存储信息，直接在 Cookie 中带过来不就好了？

这样当然可以，但把用户信息在 Cookie 中以键值对的形式传到服务端，有些麻烦。我们可以直接把所有要传的信息编码成一个字符串，这样只需要一个字段就能传递所有需要的信息了。一般，我们会把这个字段叫做 Token（令牌）。

（二）Token + 签名 -> 校验

只用一个字段就能传输所有信息，这样看起来很优雅，但这样只做到了传递信息，怎么做登录校验呢？难道服务端每次拿到用户信息后还要去查库吗？就算在库里查到了对应的信息，当初登录时服务端只生成了 Token 返回给了浏览器，并没有留下痕迹；不像 Session 校验，在服务端还留下了 Session，能证明当初“登录过”。这时候，我们就需要另一种技术了：签名。

我们可以在 Cookie 里加上一个签名字段，用户登录时，把用户信息和服务器密钥揉在一起，通过不可逆的加密算法生成签名。这样，服务端每次只需要拿着密钥去比对 Token，就能知道这个 Token 是不是自己当初生成的了。

🧠使用 Token 的工作流程：

  1. 用户登录，服务端查库校验账号密码，获得用户信息。
  2. 把用户信息通过编码生成 Token，并把用户信息和密钥加密成签名，返回给浏览器。
  3. 此后用户请求业务接口，Cookie 只携带 Token 和签名就可以。
  4. 服务端通过签名来校验 Token 合法性，进行正常业务处理。

四、JWT：标准化

虽然 Token + 签名可以做到登录校验，但这种做法额外增加了 Cookie 数量，数据本身也没有规范的格式，所以 JWT（JSON Web Token Introduction） 横空出世了。

JSON Web Token (JWT) 是一个开放标准，定义了一种传递 JSON 信息的方式。这些信息通过数字签名确保可信。

它是一种成熟的 Token 字符串生成方案，包含了我们前面提到的用户信息和签名。 不如直接看一下一个 JWT Token 长什么样：

header 声明信息，payload 是信息主体，signature 就是把 头部+载荷+密钥 揉在一起加密获得的签名，非常标准化。

这样一来，一个 Token 字段就能实现所有功能了。

五、Refresh Token：多重防护

Token，作为权限守护者，最重要的就是「安全」。

业务接口用来鉴权的 Token，我们称之为 Access Token。越是权限敏感的业务，我们越希望 Access Token 有效期足够短，以避免被盗用。但过短的有效期会造成 Access Token 经常过期，过期后怎么办呢？

一种办法是，让用户重新登录获取新 Token，显然不够友好，要知道有的 Access Token 过期时间可能只有几分钟。

另外一种办法是，再来一个 Token，一个专门生成Access Token 的 Token，我们称为 Refresh Token。

Access Token 用来访问业务接口，由于有效期足够短，盗用风险小，也可以使请求方式更宽松灵活
Refresh Token 用来获取 Access Token，有效期可以长一些，通过独立服务和严格的请求方式增加安全性。
