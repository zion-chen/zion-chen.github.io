《黑马点评》笔记01-短信登录

发表于2025-10-23|Java学习

一、为什么用 Redis 代替 Session？

在实际项目中，我们会把服务端分布式部署在多台 Tomcat 服务器上，但多台 Tomcat 并不共享 Session 存储空间，当请求切换到不同 Tomcat 服务时会出现数据丢失的问题，所以我们需要一种独立于 Tomcat 服务器之外的技术来存储登录状态。要想用其他技术替代 Session，就要满足以下几点：

  1. 数据共享
  2. 内存存储
  3. key - value 结构

答案已经呼之欲出了：Redis

二、业务逻辑

业务逻辑主要分为两部分：一是和传统网站类似的登录校验，二是加入了手机验证码登录的环节。

（一）验证码登录

验证码登录这一步骤发生在登录校验的最初始阶段，也就是“首次登录”阶段，流程如下：

  1. 服务端发送验证码
  2. 用户提交验证码
  3. 服务端校验验证码
  4. 服务端根据手机号查询用户信息（没查到就直接注册为新用户）

在步骤1和步骤2之间，服务端需要短暂保存自己发出去的验证码，才能校验用户提交的验证码是否一致，这里我们也用 Redis 进行存储。Redis 的 Key 要保证唯一性，正好用户的手机号就是唯一的，所以我们用 phone 字段作为 Key 来存储验证码。整个流程图如下：

（二）登录状态校验

传统的 Session 校验，我们是通过 Cookie 传递 SessionID，在服务端获取 Session，从而完成校验的目的。而用 Redis 的话，该怎么设计用户传来的凭证，用凭证去 Redis 里取用户信息呢？
其实这里的逻辑和 SessionID 是一样的，都是键值对的形式，只不过这里我们要自己去生成 Token，用生成的 Token 作为 Redis 中用户信息的 Key，流程如下：

  1. 登录时生成 Token，以 Token 为 Key 存储用户信息，并把 Token 写入请求头的 Authorization 字段；
  2. 在后续每次请求中，都会携带 Token 作为校验凭证，用 Token 去 Redis 中获取用户信息；
  3. 如果获取到了用户信息，则认定为用户已登录。

（二）双层拦截器

我们现在有以下两个需求：

  1. 用户在浏览网站时，有一些页面并不需要登录就可以访问，我们要把这些页面的路径在注册拦截器的时候就给排除掉；
  2. 在 Redis 中存放的 Token 必须设置 TTL，以免用户长时间没访问网站时仍旧保持登录状态，造成安全问题；
  3. 用户如果一直浏览网站，就要一直刷新 Token 的 TTL，防止登出。

乍一看，我们只需要在拦截器中对每次请求进行登录状态校验时顺便刷新 TTL 就可以了，但有些请求会被拦截器排除，如果用户一直访问这些页面，那么 Token 照样会过期。所以，我们在登录校验拦截器 LoginInterceptor 外面再加一层刷新拦截器 RefreshTokenInterceptor ，专门负责刷新 Token 的 TTL。
